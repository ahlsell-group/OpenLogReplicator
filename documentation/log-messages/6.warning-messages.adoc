==== code 60001: "incomplete row for table (obj: <number>), probably IOT, xid: <xid>, offset: <number>"

Occurs when a row cannot be reconstructed completely (common with IOTs or missing schema images).
Remediation: Ensure full schema mode or provide a schema snapshot; avoid schemaless mode for IOT tables.

==== code 60002: "unknown value (column: <column>): <number> - <data>)"

A column value could not be decoded (often seen with LOB fragments or unexpected formats).
Remediation: Enable detailed logging (`unknown=1`) to capture raw bytes and provide schema for proper decoding.

==== code 60008: "can't decode character: (x, y, z) using character set <name>, xid: <xid>"

Character data failed charset conversion at the given offset.
Remediation: Verify source character set configuration and mapping; supply correct charset if wrong.

==== code 60009: "duplicate orphaned lob: <lob>, page: <number>"

==== code 60010: "no match found for transaction rollback, skipping, SLT: <number>, USN: <number>"

Rollback record could not be matched to an open transaction.
Remediation: Usually benign if rollback started before replication; confirm retention window.

==== code 60011: "skipping transaction with no beginning, changes committed after the starting scn are lost: <details>"

Transaction began before the first redo log read and lacks a recorded start; the whole transaction is skipped, including the changes made after the starting SCN.
Logged at ERROR level because data is lost.
Remediation: Start from a checkpoint (its low watermark covers open transactions), or set `start-seq` to a redo log before the begin of the transaction.
Without a checkpoint the `online` reader starts with the redo log containing the begin of the oldest transaction open at startup (needs `SELECT` on `SYS.V_$TRANSACTION`); transactions which were open at the starting SCN but committed before startup are not covered.

==== code 60013: "forced to continue working in spite of error"

A recoverable error occurred and processing continued.
Remediation: Investigate the underlying error; check logs for details.

==== code 60018: "file: <file name> - couldn't write checkpoint"

==== code 60024: "file: <file name> - invalid header sequence (<number>, expected: <number>)"

==== code 60026: "stripping trailing '/' from <name> parameter; new value: <value>"

==== code 60029: "message size (<number>) will exceed 'max-file-size' size (<number>)"

A single generated message is larger than the writer's maximum file size.
Remediation: Increase `max-file-size` or use a writer without that limit.

==== code 60030: "rotation size is set too low (<number>), increase it, should rotate but too early (<file name>)"

Configured rotation threshold is too small and causes frequent rotations.
Remediation: Increase rotation size to reduce churn.

==== code 60031: "queue, full, sleeping <number> >ms, then retrying"

Writer queue is saturated; backpressure applied.
Remediation: Increase writer queue, improve sink throughput, or throttle source.

==== code 60032: "unknown request code: <message>"

Received an unsupported or unknown client request code.
Remediation: Verify client and server protocol versions for compatibility.

==== code 60033: "request decoder[<number>]: <data>"

Client request payload could not be decoded.
Remediation: Inspect client payload and ensure it follows the protocol.

==== code 60034: "observed UPDATE operation for NOT NULL column with NULL value for table <owner>.<table> column <column>"

Historical or partial data shows a NOT NULL column as NULL in BEFORE image.
Remediation: Usually harmless; set flag to copy AFTER into BEFORE if needed.

==== code 60035: "unknown database requested, got: <name>, expected: <name>"

Client requested a database not present in configuration.
Remediation: Client must request a configured database name.

==== code 60036: "incorrect XML data: <message>"

XMLTYPE column data could not be parsed or is malformed.
Remediation: Verify XML content and source XML dictionary metadata.

==== code 60037: "incorrect DDL data, offset: <number>"

DDL-related system data is malformed or unexpected.
Remediation: Inspect raw DDL records and source metadata; report if reproducible.

==== code 60038: "can't read SYS.V_$TRANSACTION, transactions open at the starting scn which began in earlier redo logs will be skipped"

The `online` reader could not query `SYS.V_$TRANSACTION` to find the oldest open transaction when starting without a checkpoint.
Remediation: Run `GRANT SELECT ON SYS.V_$TRANSACTION TO <user>;` (see the hint printed before this warning).

==== code 60039: "client continues from scn: <scn>, idx: <idx>, before the position it confirmed, scn: <scn>, idx: <idx>; the oldest message still held is scn: <scn>, idx: <idx>, the messages in between were released and are not sent again"

A `network` or `zeromq` client continued from a position before the one it confirmed earlier. Confirmed messages are released, so the stream resumes with the oldest message still held and the client misses the messages in between.
This happens with a client which confirms what it has read instead of what it has stored, for example the Debezium 3.6 OpenLogReplicator adapter after a task restart.
Remediation: Make the client confirm only stored positions (Debezium 3.7 or later) and restart it from an SCN before the gap. With writer option `continue-gap: 1` such a CONTINUE is refused instead.

==== code 60040: "output queue full for <seconds>s (queue-size: <number>) with messages of one transaction, scn: <scn>; a client which confirms only when the scn grows cannot confirm them; set queue-size above the number of messages of the largest transaction"

The writer queue has been full for 10 seconds with messages that all belong to one transaction (same scn). A client which confirms only when the scn grows, for example the Debezium 3.6 OpenLogReplicator adapter, cannot confirm any of them, so replication stops. Repeated every minute while the state lasts.
Remediation: Set writer `queue-size` above the number of messages of the largest transaction.

==== code 60042: "direct-path load into replicated table <owner>.<table> (obj: <number>, dataobj: <number>, scn: <scn>[-<scn>], blocks: <number>): OP 19.1 direct loader blocks are not decoded, the rows they contain are missing from the output"

A direct-path load (`INSERT /*+ APPEND */`, `INSERT /*+ APPEND_VALUES */`, SQL*Loader `direct=true`, Data Pump with the direct path access method, parallel DML) into a replicated table writes whole formatted data blocks, which the redo log carries only as OP 19.1 "Direct Loader block redo entry" records, without row-level change vectors. OpenLogReplicator does not decode these blocks, so the loaded rows never reach the output, and later changes of those rows arrive as updates or deletes of rows the consumer has never seen.
The warning is logged once per table and LWN (redo write), with the number of blocks and the scn range in that LWN; a large load gives one warning per LWN it spans. The table is looked up by the data object id of the block. A direct-path load with NOLOGGING and without FORCE LOGGING writes no redo at all and cannot be detected.
Remediation: Do not use direct-path loads on replicated tables (remove the `APPEND` hint, use conventional SQL*Loader), or resynchronize the table after the load, for example with a new snapshot of it.
