Four separate OLR restarts (SIGINT, writer checkpoint deleted), each followed by 15 s and a committed transaction. With `errors.max.retries=3` the task must still be RUNNING after the fourth restart if the retry counter resets on a successful reconnect. The delivery check counts boundary transactions written again.
This is the retriable-pattern mitigation (`internal.custom.retriable.exception`) with a bounded retry budget; whether it is safe to use depends on this scenario and olr-crash-loop. Debezium resets the retry counter only when a poll returns change data (BaseSourceTask.poll, `containsChangeDataMessages`), not on heartbeats.
